## Commit and recovery protocol

Immutable source snapshots live in each job's `.versions/{revision}/`, outside normal export output. Each includes UTF-8 source and metadata (creation time, byte count, digest and origin). A small history record identifies the first available revision and whether older legacy history is unavailable. New conversions start at version 0; existing jobs capture their current saved source without inventing earlier history.

The atomically replaced `job.properties` revision remains the commit pointer. Under the existing exclusive project lease, a save initializes the baseline if needed, checks expected revision and limits, stages and atomically publishes the next immutable snapshot, updates the working `output/main.tex` cache, then advances job metadata. File contents and the staged directory are forced before publication; destination directories are forced after atomic moves where the filesystem supports it (best effort on Windows). The previous snapshot is never overwritten.

Source reads and the ZIP's `main.tex` entry use the committed snapshot. Preview preparation restores the working cache from that snapshot before queueing the compiler. Thus a failed save cannot expose an old revision paired with new source, even if the cache advanced before metadata. On startup or before another mutation, recovery discards only staged/uncommitted snapshots above the committed revision and restores the cache from the committed snapshot. If metadata advanced before interruption, the new snapshot is retained; otherwise the old snapshot wins. Historical snapshots never come from preview directories and remain outside normal ZIP exports.

History is bounded at 100 snapshots or 100 MiB of saved source per job. A save or restore exceeding either limit returns an explicit storage-limit response; protected snapshots are never silently pruned. Restore copies selected historical text into a new increasing revision through the same commit protocol, with the current revision check and preview invalidation. Future asset history must extend this protocol consistently rather than storing mutable external paths.

## Verification

- `npm --prefix frontend run lint` and `npm --prefix frontend run build`: passed without lint or bundle-size warnings. Library and history dialogs load on demand; the main JavaScript bundle is about 486 kB minified.
- `npm --prefix frontend run test:e2e`: 58 passed across desktop and mobile Chromium. Includes save twice→preview/download→restore→reload→build/export requests, keyboard version selection, dirty-source cancel/confirm, stale second-tab restore with draft preservation, legacy/limit states and request retries, corrupt-history recovery with original/local-draft downloads, plus existing library/lifecycle/draft protections. Ten version workflows also passed in a focused run. Browser APIs are mocked; they do not prove PDF/ZIP validity.
- `./mvnw.cmd verify '-Ddoc2tex.test-pdf=true' '-Ddoc2tex.build-directory=target/roadmap-verification'`: 57 passed, zero skipped. Ten snapshot tests inject interruptions after snapshot publication, cache replacement and metadata commit, plus partial staging, then verify restart, safe retry, immutable baseline/history, canonical source/ZIP consistency, legacy migration, count/byte limits, corruption checks, and linked-path protection. A corrupt-history restart test proves the job remains listed/retrievable, its original bytes can be downloaded, unsafe source/history operations are rejected, and deletion still succeeds without overwriting damaged evidence.
- HTTP integration checks verify original version 0, version reads, explicit restore revision validation, a new restored revision/source pair, stale restore rejection and current-only ZIP source. A real Pandoc/Tectonic test saves two experiments, restores the first, builds a PDF containing the restored checkpoint and excluding the abandoned one, and checks exact ZIP source while preserving version 0. Existing Article/Report corpus fixtures remain green.
- Desktop/mobile history dialog screenshots inspected. Source preview is read only, actions fit both viewports, keyboard selection works, and opening history dismisses save toasts that could cover its mobile actions. Source/revision ownership and local draft cleanup remain in `useSourceDocument`.

CodeRabbit's initial review identified hidden jobs after recovery failure and missing directory fsync. Both were addressed before final review: failed recovery is retained as store state rather than dropping the job, original download is available independently, browser drafts survive all source-load errors, and directory entries are forced after publication. Original downloads retain the same lifecycle lease through streaming and report fetch failures inline in the source panel.

Checks use Windows with Java 25.0.1 and Node 25.5.0; CI covers Java 21 / Node 24 on Windows and Linux. All jobs and link sentinels are synthetic and isolated from real `.data` storage. Screenshots remain under ignored `frontend/test-results/`; PDF evidence is under `target/roadmap-verification/fidelity-evidence/`, including `restored-history/`. No abrupt power-loss, live screen-reader session or customer study was performed. History snapshots currently cover source only; mutable bibliography assets require the R09 manifest extension.
