# R10 Windows packaging and setup diagnostics

Started 16 October 2026 (Asia/Bangkok), after R09 merged in [PR #23](https://github.com/braces157/doc2tex/pull/23). [Issue #24](https://github.com/braces157/doc2tex/issues/24) tracks implementation. R09 final-head Windows/Linux CI passed 116 browser and 109 backend/PDF tests with no skipped tests; CodeRabbit reported no actionable findings.

## Packaging choice and redistribution

Use an x64 Windows portable ZIP containing the built frontend/application JAR, unmodified Eclipse Temurin 21.0.12.1+1 JRE, upstream runtime notices and matching OpenJDK source archive. SHA-256 pins cover both upstream runtime archives. The build manifest records version, commit, working-tree state and archive/JAR digests; a ZIP checksum accompanies the artifact. The package includes launch/stop helpers, installation/upgrade/uninstall instructions and an executable verification kit.

[Adoptium's FAQ](https://adoptium.net/docs/faq) identifies GPLv2 with Classpath Exception and permits sharing under the included licenses. Both runtime and corresponding sources come from the [same pinned release](https://github.com/adoptium/temurin21-binaries/releases/tag/jdk-21.0.12.1%2B1). Runtime component notices remain intact. [Pandoc](https://github.com/jgm/pandoc/blob/main/COPYRIGHT) is GPL-2.0-or-later, Tectonic is MIT, and [Noto fonts](https://github.com/notofonts/noto-fonts/blob/main/LICENSE) are OFL. Those converters/fonts are separately downloaded directly from upstream after an explicit download notice/choice; the candidate ZIP does not redistribute their binaries, fonts or TeX package cache. Redistribution of a populated installation needs its own complete license/source inventory.

## Behavior

- Launch uses its bundled Java, serves the built interface on loopback, and starts no downloads. Projects, immutable versions/assets, review/layout choices, downloaded tools/fonts, settings and logs live outside the app installation, under Local AppData by default. `DOC2TEX_HOME` selects a consistent external location. Development scripts remain available.
- Launcher/install locks serialize startup and tool setup. A Java lifetime file lock is acquired before Spring opens packaged project storage. Reopening verifies a live instance ID against its API; it does not trust a PID alone. Stop uses a separate local control token and graceful context shutdown. No shutdown token is exposed in system status.
- Diagnostics preserve existing system booleans while distinguishing missing/unusable tools, readable font/license presence and first-build TeX download guidance. Tool checks are bounded, capture only a short version line and perform no network installation. The lazy UI supports retries without touching source.
- The pinned compiler reproduces an offline uncached-bundle failure (`target/r10-offline-probe/compile.log`). Network/cache build failures receive connection/proxy/retry guidance; ordinary TeX failures retain source-editing guidance. Both keep source and exports available. Cache completeness and fully offline installation are not claimed.
- Explicit tool repair re-extracts a verified archive in a fresh staging folder, so a damaged existing executable is replaced rather than selected/skipped again. Package installation always uses repair mode; development setup exposes `-Repair`. A synthetic damaged Pandoc fixture is repaired during the packaged verification workflow. Bounded tool checks distinguish absent files from existing executables that cannot run.
- Upgrade instructions stop/back up first, extract into a separate app folder and retain external data/settings. Uninstall removes only the extracted app folder; data and browser drafts are retained unless the user separately removes them. No automatic updater, project migration or data-deletion script was introduced.

## Verification and release gate

Automated Windows verification removes Java/Node/npm from the launched process PATH, uses Windows PowerShell 5.1 and bundled Java, checks initial missing diagnostics, duplicate launcher/direct-runtime prevention, unauthorized shutdown, explicit checksum-verified tool/font installation, sample conversion/export, multilingual font/license export bytes, source versions, app-folder replacement and app-folder removal with external data retained. It uses a fresh synthetic evidence directory and never cleans existing project storage. The candidate package embeds the harness and multilingual fixture so it can also run on a separate machine without a development toolchain.

This host has no Windows Sandbox executable or Hyper-V management tools. A restricted-PATH host test and GitHub's development-equipped Windows runner do **not** establish clean-VM acceptance. Do not promote the candidate to a verified release or mark the clean-machine criterion complete until the checklist below has actual evidence.

Local checks passed: 112 backend/PDF tests with zero skipped and all 118 desktop/mobile browser checks before review fixes. All four diagnostics/storage checks and both setup browser checks pass after review, including retained unsaved source, corrected missing-tool tooltip and linked-storage refusal with a startup-specific error. Frontend lint/build pass with a 498.95 kB initial bundle. Setup dialogs were visually inspected at desktop/mobile sizes. The packaged lifecycle smoke passed with explicit upstream downloads, Windows PowerShell 5.1, bundled Temurin and a restricted PATH (`target/r10-smoke-v5/result.json`); it preserved two source versions, metadata, settings, original files and exact multilingual font/license export bytes through app replacement/removal. The embedded verification kit also passed entirely under Windows PowerShell 5.1, including damaged-executable repair (`target/r10-review-smoke/result.json`). Package tests found and fixed inherited PowerShell module-path and process-exit-code compatibility issues. PR review and final-head CI remain pending.

1. Start a fresh supported x64 Windows VM. Record Windows version and verify that Java/Node are not installed before copying the candidate. Do not install a JDK, Node or Maven for the check.
2. Copy/extract the candidate ZIP and verify its SHA-256. Launch before tool setup; inspect missing-tool/font guidance and confirm only loopback is listening.
3. Read the network notice, explicitly install tools/fonts, launch twice and confirm a single server. Convert the built-in sample, export it, and build a PDF with network access. Keep the package/build identity, logs and screenshots.
4. Run the included `verification/scripts/test-windows-package.ps1` with `-PackageDirectory` pointing at the extracted package, a fresh external `-EvidenceDirectory`, and `-DownloadTools`. It requires only built-in Windows PowerShell and the included runtime. Preserve result JSON, logs and sample/multilingual ZIPs. Record any OS dependency or warning; do not substitute CI success for this step.
5. Disconnect the VM before an uncached first build and verify useful network/cache guidance while source/export remain available. Reconnect and retry. A previously populated cache alone is not an offline-first-build test.
6. Save source versions and layout/review choices; stop/back up, replace with the next candidate app folder, relaunch using the same home/port and compare originals, source/assets, versions and settings. The automated harness covers same-build app-folder replacement; actual cross-version upgrade needs this check.
7. Stop and remove the extracted app folder. Confirm retained external data and browser drafts, document restoration from backup, then dispose of the synthetic VM/test data explicitly. Attach evidence to Issue #24/its PR.

macOS/Linux installers remain deferred. CI creates Windows **candidate** artifacts with checksums and smoke evidence; it does not publish a verified release automatically. Clean-VM, genuine cross-version upgrade and manual browser/OS integration remain explicit acceptance gates.
